# Interface reference

Codex Trajectory exposes three user-facing read-only MCP tools, two app-only read-only helpers, two app-only local-action tools, and one `text/html;profile=mcp-app` resource at `ui://codex-trajectory/trajectory-v2.html`. The resource uses the widget-state bridge for guard persistence and, only after explicit CDP opt-in, the private `request_codex_task_stop` action. Trajectory and live-update tools remain read-only. The private setting tool writes only plugin-owned CDP configuration; the private stop tool may pause the bound task's Goal and interrupt its active turn, but neither edits task logs.

## Session resolution

Session identifiers must exactly match or unambiguously prefix an identifier discovered below `CODEX_HOME/sessions`; archived target sessions are considered only when `includeArchived` is true. Whitespace surrounding an identifier is ignored, but empty values and strings containing `/` or `\\` are rejected. Exact matches return immediately. Prefix matches must resolve to one target or fail as ambiguous. File paths are never accepted.

Discovery first resolves each configured session root, then accepts only regular files with one filesystem link whose descriptor-checked component chain and final path remain below that root. Descendant symbolic links, reparse points, file hardlinks, FIFOs, and other non-regular sources are excluded. Discovery is capped at 100,000 entries, 10,000 directories, depth 64, and 10,000 rollout files per request. Compact overviews are cached against descriptor-derived modification time, size, and change time for every file in a rollout lineage, so a changed inherited segment invalidates the cache.

When `list_codex_sessions` receives a non-empty query, discovery filters title, identifier, display-safe working directory, and model through a private metadata index before building full overviews. An index miss scans the complete rollout but decodes only metadata-bearing JSONL records; matched candidates alone receive a full overview, and scanning stops at `limit`. The index at `CODEX_HOME/codex-trajectory/session-search-index-v1.json` stores hashed physical and lineage identities, lineage file metadata signatures, and those four bounded search fields. It contains no transcript bodies, tool details, reasoning, Git metadata, or absolute log paths; it is capped at 10,000 entries and 8 MiB, written atomically with mode 0600, rejects linked files, and fails open to an uncached scan. Any lineage signature change invalidates the corresponding entry.

## Rollout formats

Legacy single-file JSONL and Codex paginated history are both supported in plain `.jsonl` and Zstandard-compressed `.jsonl.zst` files. Python 3.14 uses `compression.zstd`; Python 3.10–3.13 use the pinned `zstandard==0.25.0` dependency. Decompression is materialized into an 8 MiB memory spool that spills to a private temporary file, with a 128 MiB window cap and a 512 MiB decompressed hard limit; concatenated frames are accepted, while truncation and trailing garbage fail closed. `history_base.end_byte_offset` always addresses the decompressed logical JSONL stream.

A paginated target is joined oldest-first through official `history_base` pointers, up to 1,024 segments. Current filenames may end in `<thread_uuid>_<rollout_uuid>`: leading metadata must match the thread UUID, while lineage references resolve the immutable rollout UUID. Every segment must use paginated mode, begin at the declared ordinal, remain contiguous, and end exactly at both the declared ordinal and complete-line byte boundary. Paginated wire records without valid leading paginated session metadata, or a missing, ambiguous, cyclic, truncated, overlong, or inconsistent lineage, fail closed. Legacy metadata may appear within the bounded ten-line header probe; paginated metadata must be the leading record. A lineage source may be resolved from either authorized session root even when the selected target is active.

For paginated subagent rollouts, every lineage segment applies its own `subagent_history_start_ordinal`; earlier records in that segment are inherited model context rather than the segment's agent activity and are excluded. This prevents a fork or revert of a migrated subagent from re-exposing the parent's copied context. The target file's first `session_meta` always owns the returned session identity and metadata; an inherited parent's metadata cannot replace it.

## Detail levels

`summary` is the default. It omits record input, output, and metadata; log source paths and Git remotes are never part of the public response. `full` includes bounded record details up to 12,000 characters per field. Both modes exclude `session_meta.base_instructions` and encrypted reasoning content. Persisted reasoning summaries remain visible.

## Projection behavior

`schemaVersion` is `2`. Version 2 adds the required `cost` estimate fields to task statistics, turns, and records. The closed [version 1 schema](../schemas/trajectory-v1.schema.json) remains unchanged for existing validators, while current responses follow the [version 2 schema](../schemas/trajectory-v2.schema.json). Turns use `task_started`, `task_complete`, and `turn_aborted` events where available. Because Codex rollout logs do not persist an authoritative model-step identifier, the projection begins step one with the first model response and increments the approximate step after a tool result when model output resumes.

Tool duration is measured between persisted call and output timestamps unless a completion event provides a duration. A completed record with only one persisted event timestamp has `durationMs: null` because no elapsed interval was measured; a persisted interval that genuinely measures zero remains `0`, while a positive duration below one millisecond is represented as `1`. Explicit completion failures, including MCP `result.Err` values, remain failures when the later tool output is projected. Unknown event types are ignored. A malformed complete JSONL or UTF-8 line produces a warning; an incomplete final JSON or UTF-8 line without a newline is treated as an in-progress write and silently deferred.

The projection recognizes the persisted legacy events and current canonical turn items for user and hook prompts, assistant messages and plans, reasoning summaries, command execution, dynamic and MCP tools, collaboration/subagent activity, web search, image view/generation, extension actions, file changes, review-mode boundaries, and context compaction. A paginated raw `AgentMessage` is also retained because current Codex uses it for inter-agent communication without a canonical turn-item counterpart. Persisted control or metadata events without a user-visible ledger representation are intentionally ignored; `thread_rolled_back` instead emits a warning that earlier projected execution remains a historical record. Canonical `item_completed` records own their declared turn; a mismatched turn closes the prior turn as aborted so overview and detail counts do not diverge.

Each persisted `last_token_usage` object is attached to the latest model record and accumulated into the owning turn's `usage` only when its accompanying cumulative `total_token_usage` snapshot changes; repeated cumulative snapshots and initial zero snapshots are ignored. When older logs omit a cumulative snapshot, the `last_token_usage` sample retains the legacy behavior and is counted. `modelCalls` counts the accepted usage samples. Each turn also captures the model active in its `turn_context`, falling back to the session model in the viewer. The viewer displays each request's uncached input, cached input, and output in separate columns on the matching indexed ledger row, while each turn header displays the corresponding three per-turn totals. Uncached input is derived as `max(0, input_tokens - cached_input_tokens)`. Session totals continue to come from the latest `total_token_usage`. Cached-input and reasoning-output values are breakdowns within input and output, so clients must not add them to `total_tokens`. Cumulative session input is not a context-window measurement.

Every accepted usage sample is also priced against an explicit allowlist snapshot of standard OpenAI API text-token rates, updated 2026-08-24. The snapshot uses GPT-5.6 Sol's current promotional standard rate, advertised through at least 2026-11-21. The matching model record receives `record.cost`, `turn.cost` accumulates the owning turn, and `stats.cost` accumulates the complete parsed task independently of record pagination. Each estimate reports USD totals for uncached input, cached input, and output; reasoning output is already included in output and is not charged twice. `coverage` is `complete`, `partial`, or `unavailable`, with priced and unpriced model-call counts. Exact published model IDs and dated snapshots are supported; unknown and Codex-only model aliases without a published API rate remain unpriced instead of inheriting a guessed family rate. The estimate uses standard token pricing only and is not a Codex subscription bill. Tool-call fees, cache writes, long-context multipliers, Batch/Flex/Fast tiers, and regional processing adjustments are excluded. Pricing is local and performs no runtime network lookup.

The latest valid persisted `rate_limits` snapshot is exposed as `stats.rateLimits`. Only the bounded `primary` and `secondary` windows are projected, each with `usedPercent`, `windowMinutes`, and an optional normalized `resetsAt`; plan, credit, account, and unknown fields are excluded. Partial valid snapshots update only their valid windows. The live viewer calculates remaining allowance as `max(0, 100 - usedPercent)` and never substitutes Token totals or the model context window when account quota data is absent.

The log is parsed incrementally, and only one `maxRecords` page is retained and returned with stable original `index` values. Without `beforeRecord`, this is the newest tail. With an exclusive `beforeRecord` index, the response contains the closest preceding records whose indexes are lower than the cursor. The `pagination` object reports the first and last returned indexes, earlier and later record counts, both direction flags, and `nextBeforeRecord`; pass that next cursor unchanged to retrieve the adjacent older page. Aggregate statistics continue to describe the complete parsed task, independent of page selection. At most 1,000 records and 1,000 visible turns are returned per response; every visible record's owning turn is retained before remaining slots are filled with the newest turns. Warnings are capped at 100, and active tool correlation is bounded independently of the page so projection indexes do not change between page requests. Text summaries and full-detail fields are bounded independently. A logical rollout is capped at 512 MiB and 1,000,000 physical lines; each complete JSONL line is capped at 16 MiB. Duplicate object keys, `NaN`/infinity, floats outside the finite range, integers over 256 digits, and non-object records are never projected as valid entries.

`get_codex_trajectory` and `show_codex_trajectory` do not eagerly attach recent-session overviews to the trajectory payload. After the selected trajectory has rendered, the viewer makes one `list_codex_sessions` request for its selector. The optional schema-v1 `recentSessions` property remains accepted for backward-compatible callers.

The viewer targets Codex desktop surfaces and desktop Chromium browsers. It initially materializes ledger records for the latest loaded turn only. Earlier turn headers remain available, and clicking anywhere on a turn summary row—including its uncached-input, cache-read, and output totals—adds or removes that turn's records from the DOM; filtering or selecting a hidden record reveals it automatically. Each expanded turn materializes its own sticky ledger-column header, scoped to that turn's row group. Record rows therefore show only the approximate Step, while the owning turn remains visible in the group header and full Turn/step context remains in the inspector. Event and Content use compact proportional columns so the complete ledger fits its viewport without horizontal scrolling; truncated values are available through a viewport-level hover tooltip, and record focus exposes both values. Large session Token totals use responsive tabular-number sizing and are never ellipsized; the per-turn Token table expands horizontally when exact values need more room. The collapsed per-turn table is materialized only when opened. Viewer-initiated full refreshes request the default 500-record tail rather than the 1,000-record maximum. When earlier records exist, **Load earlier records** requests the adjacent 500-record page, merges records and turns by stable index, deduplicates warnings, and compensates for the prepended ledger height so the current viewport remains anchored.

## Adaptive live window

The **Live window** control selects the presentation supported by its current host from an explicit user gesture. When the Codex display bridge is present, it requests `fullscreen` and fills that host-managed side panel. The non-scrolling upper region contains the task title, live state, current turn/approximate step/stable record index, record and turn counts, cumulative Token totals, total estimated cost, and current-turn estimated cost. If projected rate-limit windows are available, an upper-right quota badge shows each window's remaining percentage and exposes its reset time in a tooltip; otherwise the badge is hidden.

The Codex side panel also renders a one-click stop button plus an optional auto-stop guard. Both controls require the explicitly enabled loopback CDP integration; while it is disabled or disconnected, the controls are disabled and the component never substitutes `sendFollowUpMessage`. The guard defaults to disabled with a whole-percentage threshold of 10, accepts values from 1 through 100, and evaluates `remaining <= threshold` across every valid displayed limit window after live refreshes. A trigger key combines the displayed session, configured threshold, and each displayed window's duration and reset timestamp; it intentionally excludes the running-turn identity. The component saves that key with the enabled state and threshold through `window.openai.setWidgetState`, preventing repeated requests across later turns in the same quota cycle. The standard Apps resource calls the app-private `request_codex_task_stop` tool through the MCP Apps tool bridge. That path reads `thread/goal/get`, requires an active Goal to be changed to `paused` through `thread/goal/set`, then calls `turn/interrupt`; it may bootstrap a missing projected turn and rebind one rejected stale candidate before retrying. A confirmed active Goal that cannot be paused is left running and reported as an error rather than creating an interrupt/continuation loop. A later running turn rearms manual stopping without clearing the automatic quota-cycle latch. Disabling or changing the guard rearms it, observing all windows above the threshold clears the latch, and a changed quota reset timestamp creates a new cycle. Transient automatic failures do not consume the latch and retry with exponential delays bounded from 2 to 30 seconds. Successful manual stops also satisfy an already-active automatic quota cycle, preventing the guard from immediately stopping a Goal continuation.

The standard Apps surface uses no task message as a stopping primitive: it calls only the private, app-visible `request_codex_task_stop` MCP tool. The action accepts no prompt text, does not depend on a sidebar DOM selection, and sends nothing into the steering queue. The viewer binds stopping to the session that opened it, selecting another trajectory disables both controls, and the native video PiP surface omits them because it is not interactive. Auto-stop reacts to the first live snapshot that records a threshold crossing; the one-second polling interval cannot make persisted rate-limit events more granular.

A flex-height event region below the fixed controls scrolls independently through the bounded safe-summary tail in chronological order. Sticky turn dividers show each visible turn's Token total and estimated cost; every row includes status, duration, and its own Token delta and estimated cost when recorded. That delta is arranged as Total, Estimated cost, Input, and Output rows, with uncached/cache details under Input and visible/reasoning details under Output. Follow-latest keeps the newest row at the bottom, but preserves the user's position while they read older rows. A compact transparent 8-by-4 sprite sheet stays clipped inside the newest card's upper-left corner: its 32-frame mining cycle starts when that record's stable identity changes, returns to the first frame after one cycle, does not restart on an unchanged poll, and is suppressed by `prefers-reduced-motion`. The side-panel shell remains mounted and patches only changed fields and record content, keeping the fixed status row stable across one-second checks. The component never requests the unsupported `pip` host mode. When the bridge is absent, it captures a 2:3 canvas as a MediaStream, draws the task, current-turn, and latest-record cost estimates with the compact quota summary, feeds the canvas to a hidden video element, and requests Chromium's native always-on-top picture-in-picture window. Neither path launches a standalone application, and a full-detail inline payload is never copied into either live surface. Closing the native window, returning the host to `inline`, or using the component's close control stops live scheduling and refreshes the inline viewer at the detail level that was active before entry.

The app-only `get_codex_trajectory_update` tool accepts `sessionId`, optional `includeArchived`, and an optional 64-character opaque `revision`. Its descriptor uses `ui.visibility: ["app"]`, so it supports the component without becoming a user-facing model tool. The first call, or a call after any lineage file changes, returns a `summary` trajectory capped at 50 latest records plus the next revision. A matching revision returns only `{schemaVersion, unchanged, revision}` and avoids projection parsing. The component issues at most one request at a time every second, stops scheduling while the document is hidden or after the live window exits, resumes immediately when visible, and exponentially backs off to 30 seconds after repeated failures. A source change still requires a complete streaming projection scan to maintain aggregate statistics.

## Optional CDP direct-stop integration

The app-private stop contract accepts `{sessionId, turnId?, source, threshold, language}`. It refuses to act while the persisted opt-in is disabled. A missing candidate is bootstrapped through a history-free state read, and an exact stale-turn rejection may rebind once before retrying. Calls use one absolute deadline across discovery, WebSocket setup, target traversal, Goal access, and interrupt verification; trickle responses cannot reset that budget. A disabled setting is rechecked before any stop transport is attempted.

The inline viewer exposes an experimental, off-by-default switch backed by the app-only `get_codex_toolbar_injection_status` and `set_codex_toolbar_injection` tools. The setter accepts `enabled` plus a loopback port from 1024 through 65535 and atomically stores only `{schemaVersion, enabled, port}` in a mode-0600 plugin-owned file beneath `CODEX_HOME/codex-trajectory`. A bounded cross-process control lock serializes settings, recovery, and watcher replacement; settings revisions prevent an older process from restoring an obsolete enable/port choice. A second bounded status file reports the watcher's PID, runtime identity, connection booleans, a fixed public error category, and a timestamp. It never contains transcript content, credentials, exception text, or absolute paths. `cdpAvailable` is probed only while enabled; Windows process liveness uses a process handle rather than a console signal. The read-only status helper never starts a process.

The watcher connects only to `127.0.0.1`/`localhost` CDP HTTP and WebSocket endpoints, rejects non-loopback debugger URLs, and never follows HTTP redirects during discovery. While enabled it scans at most 100 page/iframe/webview targets once per second, evaluates the token-bearing guarded injector only in Codex-owned `app://` renderers, removes stale injector state from other targets, tries every eligible renderer before reporting bridge failure, and survives SPA/React replacement with a scoped `MutationObserver`. Each WebSocket command has an absolute deadline even if unrelated CDP events continue arriving. It also binds an ephemeral `127.0.0.1` HTTP port and serves a small wrapper plus the exact bundled trajectory app resource beneath a random 256-bit URL token. A same-origin tool bridge accepts bounded interoperable JSON POSTs for only `list_codex_sessions`, `get_codex_trajectory`, `get_codex_trajectory_update`, `get_codex_toolbar_injection_status`, and `set_codex_toolbar_injection`; duplicate keys and non-finite or oversized numbers are rejected, and all normal MCP argument validation and projection bounds still apply. A read-only theme route accepts no inputs and samples a fixed allowlist of computed Codex CSS colors for the effective background, surfaces, borders, text, accent, success, danger, and event categories. A separate read-only task-state route accepts exactly one bounded session identifier plus an optional bounded turn candidate, reads that bound task through App Server, and returns only a running boolean plus a bounded turn identifier or null. It lets controls follow App Server task activity while the log-derived ledger is delayed. The theme route returns exactly the validated `light`/`dark` effective scheme plus those bounded colors, allowing Codex's System, Light, and Dark appearance choices to update an already-open Browser tab without persisting the palette. A separate stop route accepts exactly `{sessionId, turnId, source, threshold, language}` with bounded identifiers, `manual`/`auto` enum, integer 1–100 threshold, and `en`/`zh` locale. It rejects extra keys and never accepts prompt text. Requests require the exact loopback Host header and token; responses disable caching and apply separate restrictive parent/viewer CSPs. The token is held only in memory and is never written to the status file.

The token-bearing Codex in-app Browser shortcut reports `browserShortcutAvailable: true` only on macOS and Windows. Startup must first discover an authenticated Codex desktop ancestor; Windows continues through multiple qualifying packaged `codex.exe`/`ChatGPT.exe` ancestors and pins the outer desktop root so a parent-owned CDP listener and the plugin process share the same trusted ancestry. Each token-bearing WebSocket connection then resolves the exact server-side PID from its TCP four-tuple and accepts only that pinned host or a verified descendant. The pinned identity includes process creation identity and executable path to reject PID reuse. macOS also verifies the `com.openai.codex` application against OpenAI's signing team, while Windows requires the `OpenAI.Codex` package family on the host and every accepted descendant. The check runs before the WebSocket handshake carries the viewer URL/token. Missing, ambiguous, stale, mismatched, or unsupported identities fail closed without sending the local viewer URL/token or creating token-bearing injection; if every shell target fails authentication, the heartbeat exposes only the fixed public error category. Direct stop and the fixed `REMOVE_SOURCE` cleanup do not carry the trajectory bearer token and remain separate. A runtime revision forces same-path upgrades to replace an older watcher.

The app must be launched with a loopback `--remote-debugging-port` before direct stop can connect. Enabling the setting does not change the app executable, relaunch the app, bind a network listener, or expose the selected port. CDP grants broad page control to local processes, so users must keep it on loopback, avoid tunnels, and trust the selected local endpoint. Composer drafts and attachments remain untouched.

The plugin intentionally bundles no lifecycle command hook. Each MCP server startup serves protocol requests immediately, then reconciles the already opted-in watcher and prewarms the latest bounded safe-summary projection in a daemon worker. The recovery still uses the existing windowless-interpreter/`CREATE_NO_WINDOW` supervisor path. The packaged MCP command is a portable relative launcher: its Unix implementation uses `exec uv`, while its reviewed Windows GUI-subsystem implementation prefers Astral's stdio-preserving `uvw.exe` and falls back to `uv.exe` with `CREATE_NO_WINDOW`. Both preserve the inherited MCP stdio handles. The watcher supervisor selects the base installation's `pythonw.exe` and supplies the active uv script environment through `PYTHONPATH`, rather than launching the venv `pythonw.exe` redirector that can create a console-subsystem `python.exe` child. This removes all observed console launch points that could leave a Windows Terminal/`cmd.exe` tab while preserving automatic shortcut recovery and Linux/macOS startup. Safe projections are cached only under immutable lineage file signatures and returned by copy; an append changes the key and forces reprojection. An authenticated runtime upgrade starts the replacement viewer and writes only a private runtime-identity readiness marker before the verified old watcher is stopped, then waits for the shared watcher lock and the supervisor's temporary settings toggle to finish. First injection exits after installing the authenticated shell shortcut and defers auxiliary-renderer cleanup to the next cycle. The cross-process watcher and supervisor locks make concurrent startup idempotent, and settings revisions preserve later disable or port changes. Public status exposes only bounded startup durations, not absolute timestamps or the viewer bearer-token URL. Recovery neither enables the setting nor sends a trajectory token; authentication or launch failure is suppressed so the read-only MCP path still starts.

## Transport limits

The bundled stdio server implements MCP protocol revision `2025-06-18`, where JSON-RPC batching is not supported. Each newline-delimited request is UTF-8, limited to 8 MiB, and decoded with the same strict duplicate-key and numeric rules as session logs. Every encoded response, including its newline, is also limited to 8 MiB; oversized successful results become a bounded error, so callers should paginate rather than request an unbounded full transcript. Requests require a non-null string or finite numeric ID; notifications omit the ID and receive no response. The reader observes cancellation notifications while one request is executing and suppresses cancelled responses, but projection work remains serial and is not preempted. Malformed JSON, invalid requests, invalid parameters, unknown methods/resources, and internal failures use stable JSON-RPC error classes without exposing local filesystem details.
