# Interface reference

Codex Trajectory exposes three user-facing read-only MCP tools, one app-only read-only live-update tool, and one `text/html;profile=mcp-app` resource at `ui://codex-trajectory/trajectory-v1.html`.

## Session resolution

Session identifiers must exactly match or unambiguously prefix an identifier discovered below `CODEX_HOME/sessions`; archived target sessions are considered only when `includeArchived` is true. Whitespace surrounding an identifier is ignored, but empty values and strings containing `/` or `\\` are rejected. Exact matches return immediately. Prefix matches must resolve to one target or fail as ambiguous. File paths are never accepted.

Discovery first resolves each configured session root, then accepts only regular files with one filesystem link whose descendant component chain and canonical path remain below that root. Descendant symbolic links and file hardlinks are excluded. Compact overviews are cached against modification time, size, and change time for every file in a rollout lineage, so a changed inherited segment invalidates the cache.

## Rollout formats

Legacy single-file JSONL and Codex paginated history are both supported. A paginated target is joined oldest-first through official `history_base` pointers, up to 1,024 segments. Every segment must use paginated mode, carry a metadata ID equal to the UUID in its canonical filename, begin at the declared ordinal, remain contiguous, and end exactly at both the declared ordinal and complete-line byte boundary. Paginated wire records without valid leading paginated session metadata, or a missing, ambiguous, cyclic, truncated, overlong, or inconsistent lineage, fail closed. A lineage source may be resolved from either authorized session root even when the selected target is active.

For paginated subagent rollouts, every lineage segment applies its own `subagent_history_start_ordinal`; earlier records in that segment are inherited model context rather than the segment's agent activity and are excluded. This prevents a fork or revert of a migrated subagent from re-exposing the parent's copied context. The target file's first `session_meta` always owns the returned session identity and metadata; an inherited parent's metadata cannot replace it.

## Detail levels

`summary` is the default. It omits record input, output, and metadata; log source paths and Git remotes are never part of the public response. `full` includes bounded record details up to 12,000 characters per field. Both modes exclude `session_meta.base_instructions` and encrypted reasoning content. Persisted reasoning summaries remain visible.

## Projection behavior

`schemaVersion` is `1`. Turns use `task_started`, `task_complete`, and `turn_aborted` events where available. Because Codex rollout logs do not persist an authoritative model-step identifier, the projection begins step one with the first model response and increments the approximate step after a tool result when model output resumes.

Tool duration is measured between persisted call and output timestamps unless a completion event provides a duration. Explicit completion failures, including MCP `result.Err` values, remain failures when the later tool output is projected. Unknown event types are ignored. A malformed complete JSONL or UTF-8 line produces a warning; an incomplete final JSON or UTF-8 line without a newline is treated as an in-progress write and silently deferred.

The projection recognizes the persisted legacy events and current canonical turn items for user and hook prompts, assistant messages and plans, reasoning summaries, command execution, dynamic and MCP tools, collaboration/subagent activity, web search, image view/generation, extension actions, file changes, review-mode boundaries, and context compaction. A paginated raw `AgentMessage` is also retained because current Codex uses it for inter-agent communication without a canonical turn-item counterpart. Persisted control or metadata events without a user-visible ledger representation are intentionally ignored; `thread_rolled_back` instead emits a warning that earlier projected execution remains a historical record. Canonical `item_completed` records own their declared turn; a mismatched turn closes the prior turn as aborted so overview and detail counts do not diverge.

Each persisted `last_token_usage` object is attached to the latest model record and accumulated into the owning turn's `usage` only when its accompanying cumulative `total_token_usage` snapshot changes; repeated cumulative snapshots and initial zero snapshots are ignored. When older logs omit a cumulative snapshot, the `last_token_usage` sample retains the legacy behavior and is counted. `modelCalls` counts the accepted usage samples. Each turn also captures the model active in its `turn_context`, falling back to the session model in the viewer. The viewer displays each request's uncached input, cached input, and output in separate columns on the matching indexed ledger row, while each turn header displays the corresponding three per-turn totals. Uncached input is derived as `max(0, input_tokens - cached_input_tokens)`. Session totals continue to come from the latest `total_token_usage`. Cached-input and reasoning-output values are breakdowns within input and output, so clients must not add them to `total_tokens`. Cumulative session input is not a context-window measurement.

The log is parsed incrementally, and only one `maxRecords` page is retained and returned with stable original `index` values. Without `beforeRecord`, this is the newest tail. With an exclusive `beforeRecord` index, the response contains the closest preceding records whose indexes are lower than the cursor. The `pagination` object reports the first and last returned indexes, earlier and later record counts, both direction flags, and `nextBeforeRecord`; pass that next cursor unchanged to retrieve the adjacent older page. Aggregate statistics continue to describe the complete parsed task, independent of page selection. At most 1,000 records and 1,000 visible turns are returned per response; every visible record's owning turn is retained before remaining slots are filled with the newest turns. Warnings are capped at 100, and active tool correlation is bounded independently of the page so projection indexes do not change between page requests. Text summaries and full-detail fields are bounded independently. JSONL lines are capped at 16 MiB; duplicate object keys, `NaN`/infinity, floats outside the finite range, integers over 256 digits, and non-object records are never projected as valid entries.

The viewer initially materializes ledger records for the latest loaded turn only. Earlier turn headers remain available, and clicking anywhere on a turn summary row—including its uncached-input, cache-read, and output totals—adds or removes that turn's records from the DOM; filtering or selecting a hidden record reveals it automatically. Each expanded turn materializes its own sticky ledger-column header, scoped to that turn's row group. Record rows therefore show only the approximate Step, while the owning turn remains visible in the group header and full Turn/step context remains in the inspector. Event and Content use compact proportional columns so the complete ledger fits its viewport without horizontal scrolling; truncated values are available through a viewport-level hover tooltip, and record focus exposes both values. Large session Token totals use responsive tabular-number sizing and are never ellipsized; the per-turn Token table expands horizontally when exact values need more room. The collapsed per-turn table is materialized only when opened. Viewer-initiated full refreshes request the default 500-record tail rather than the 1,000-record maximum. When earlier records exist, **Load earlier records** requests the adjacent 500-record page, merges records and turns by stable index, deduplicates warnings, and compensates for the prepended ledger height so the current viewport remains anchored.

## Adaptive live window

The **Live window** control selects the presentation supported by its current host from an explicit user gesture. When the Codex display bridge is present, it requests `fullscreen` and fills that host-managed side panel. The non-scrolling upper region contains the task title, live state, current turn/approximate step/stable record index, record and turn counts, and cumulative Token totals. A flex-height event region below it scrolls independently through the bounded safe-summary tail in chronological order; every row includes status, duration, and its own Token delta when recorded. That delta is arranged as Total, Input, and Output rows, with uncached/cache details under Input and visible/reasoning details under Output. Follow-latest keeps the newest row at the bottom, but preserves the user's position while they read older rows. The side-panel shell remains mounted and patches only changed fields and record content, keeping the fixed status row stable across one-second checks. The component never requests the unsupported `pip` host mode. When the bridge is absent, it captures a 2:3 canvas as a MediaStream, feeds it to a hidden video element, and requests Chromium's native always-on-top picture-in-picture window. Neither path launches a standalone application, and a full-detail inline payload is never copied into either live surface. Closing the native window, returning the host to `inline`, or using the component's close control stops live scheduling and refreshes the inline viewer at the detail level that was active before entry.

The app-only `get_codex_trajectory_update` tool accepts `sessionId`, optional `includeArchived`, and an optional 64-character opaque `revision`. Its descriptor uses `ui.visibility: ["app"]`, so it supports the component without becoming a user-facing model tool. The first call, or a call after any lineage file changes, returns a `summary` trajectory capped at 50 latest records plus the next revision. A matching revision returns only `{schemaVersion, unchanged, revision}` and avoids projection parsing. The component issues at most one request at a time every second, stops scheduling while the document is hidden or after the live window exits, resumes immediately when visible, and exponentially backs off to 30 seconds after repeated failures. A source change still requires a complete streaming projection scan to maintain aggregate statistics.

## Transport limits

The bundled stdio server implements MCP protocol revision `2025-06-18`, where JSON-RPC batching is not supported. Each newline-delimited request is UTF-8, limited to 8 MiB, and decoded with the same strict duplicate-key and numeric rules as session logs. Requests require a non-null string or finite numeric ID; notifications omit the ID and receive no response. Malformed JSON, invalid requests, invalid parameters, unknown methods, and internal failures use their standard JSON-RPC error classes without exposing local filesystem details.
