# Interface reference

Codex Trajectory exposes three user-facing read-only MCP tools, two app-only read-only helpers, one app-only local-setting tool, and one `text/html;profile=mcp-app` resource at `ui://codex-trajectory/trajectory-v1.html`. The resource can optionally use the Codex host's follow-up-message and widget-state bridge methods or the configured in-app Browser's constrained stop bridge. Trajectory and live-update tools remain read-only; the private setting tool writes only plugin-owned CDP configuration and never edits task logs.

## Session resolution

Session identifiers must exactly match or unambiguously prefix an identifier discovered below `CODEX_HOME/sessions`; archived target sessions are considered only when `includeArchived` is true. Whitespace surrounding an identifier is ignored, but empty values and strings containing `/` or `\\` are rejected. Exact matches return immediately. Prefix matches must resolve to one target or fail as ambiguous. File paths are never accepted.

Discovery first resolves each configured session root, then accepts only regular files with one filesystem link whose descendant component chain and canonical path remain below that root. Descendant symbolic links and file hardlinks are excluded. Compact overviews are cached against modification time, size, and change time for every file in a rollout lineage, so a changed inherited segment invalidates the cache.

## Rollout formats

Legacy single-file JSONL and Codex paginated history are both supported. A paginated target is joined oldest-first through official `history_base` pointers, up to 1,024 segments. Every segment must use paginated mode, carry a metadata ID equal to the UUID in its canonical filename, begin at the declared ordinal, remain contiguous, and end exactly at both the declared ordinal and complete-line byte boundary. Paginated wire records without valid leading paginated session metadata, or a missing, ambiguous, cyclic, truncated, overlong, or inconsistent lineage, fail closed. A lineage source may be resolved from either authorized session root even when the selected target is active.

For paginated subagent rollouts, every lineage segment applies its own `subagent_history_start_ordinal`; earlier records in that segment are inherited model context rather than the segment's agent activity and are excluded. This prevents a fork or revert of a migrated subagent from re-exposing the parent's copied context. The target file's first `session_meta` always owns the returned session identity and metadata; an inherited parent's metadata cannot replace it.

## Detail levels

`summary` is the default. It omits record input, output, and metadata; log source paths and Git remotes are never part of the public response. `full` includes bounded record details up to 12,000 characters per field. Both modes exclude `session_meta.base_instructions` and encrypted reasoning content. Persisted reasoning summaries remain visible.

## Projection behavior

`schemaVersion` is `1`. Turns use `task_started`, `task_complete`, and `turn_aborted` events where available. Because Codex rollout logs do not persist an authoritative model-step identifier, the projection begins step one with the first model response and increments the approximate step after a tool result when model output resumes.

Tool duration is measured between persisted call and output timestamps unless a completion event provides a duration. A completed record with only one persisted event timestamp has `durationMs: null` because no elapsed interval was measured; a persisted interval that genuinely measures zero remains `0`. Explicit completion failures, including MCP `result.Err` values, remain failures when the later tool output is projected. Unknown event types are ignored. A malformed complete JSONL or UTF-8 line produces a warning; an incomplete final JSON or UTF-8 line without a newline is treated as an in-progress write and silently deferred.

The projection recognizes the persisted legacy events and current canonical turn items for user and hook prompts, assistant messages and plans, reasoning summaries, command execution, dynamic and MCP tools, collaboration/subagent activity, web search, image view/generation, extension actions, file changes, review-mode boundaries, and context compaction. A paginated raw `AgentMessage` is also retained because current Codex uses it for inter-agent communication without a canonical turn-item counterpart. Persisted control or metadata events without a user-visible ledger representation are intentionally ignored; `thread_rolled_back` instead emits a warning that earlier projected execution remains a historical record. Canonical `item_completed` records own their declared turn; a mismatched turn closes the prior turn as aborted so overview and detail counts do not diverge.

Each persisted `last_token_usage` object is attached to the latest model record and accumulated into the owning turn's `usage` only when its accompanying cumulative `total_token_usage` snapshot changes; repeated cumulative snapshots and initial zero snapshots are ignored. When older logs omit a cumulative snapshot, the `last_token_usage` sample retains the legacy behavior and is counted. `modelCalls` counts the accepted usage samples. Each turn also captures the model active in its `turn_context`, falling back to the session model in the viewer. The viewer displays each request's uncached input, cached input, and output in separate columns on the matching indexed ledger row, while each turn header displays the corresponding three per-turn totals. Uncached input is derived as `max(0, input_tokens - cached_input_tokens)`. Session totals continue to come from the latest `total_token_usage`. Cached-input and reasoning-output values are breakdowns within input and output, so clients must not add them to `total_tokens`. Cumulative session input is not a context-window measurement.

The latest valid persisted `rate_limits` snapshot is exposed as `stats.rateLimits`. Only the bounded `primary` and `secondary` windows are projected, each with `usedPercent`, `windowMinutes`, and an optional normalized `resetsAt`; plan, credit, account, and unknown fields are excluded. Partial valid snapshots update only their valid windows. The live viewer calculates remaining allowance as `max(0, 100 - usedPercent)` and never substitutes Token totals or the model context window when account quota data is absent.

The log is parsed incrementally, and only one `maxRecords` page is retained and returned with stable original `index` values. Without `beforeRecord`, this is the newest tail. With an exclusive `beforeRecord` index, the response contains the closest preceding records whose indexes are lower than the cursor. The `pagination` object reports the first and last returned indexes, earlier and later record counts, both direction flags, and `nextBeforeRecord`; pass that next cursor unchanged to retrieve the adjacent older page. Aggregate statistics continue to describe the complete parsed task, independent of page selection. At most 1,000 records and 1,000 visible turns are returned per response; every visible record's owning turn is retained before remaining slots are filled with the newest turns. Warnings are capped at 100, and active tool correlation is bounded independently of the page so projection indexes do not change between page requests. Text summaries and full-detail fields are bounded independently. JSONL lines are capped at 16 MiB; duplicate object keys, `NaN`/infinity, floats outside the finite range, integers over 256 digits, and non-object records are never projected as valid entries.

The viewer initially materializes ledger records for the latest loaded turn only. Earlier turn headers remain available, and clicking anywhere on a turn summary row—including its uncached-input, cache-read, and output totals—adds or removes that turn's records from the DOM; filtering or selecting a hidden record reveals it automatically. Each expanded turn materializes its own sticky ledger-column header, scoped to that turn's row group. Record rows therefore show only the approximate Step, while the owning turn remains visible in the group header and full Turn/step context remains in the inspector. Event and Content use compact proportional columns so the complete ledger fits its viewport without horizontal scrolling; truncated values are available through a viewport-level hover tooltip, and record focus exposes both values. Large session Token totals use responsive tabular-number sizing and are never ellipsized; the per-turn Token table expands horizontally when exact values need more room. The collapsed per-turn table is materialized only when opened. Viewer-initiated full refreshes request the default 500-record tail rather than the 1,000-record maximum. When earlier records exist, **Load earlier records** requests the adjacent 500-record page, merges records and turns by stable index, deduplicates warnings, and compensates for the prepended ledger height so the current viewport remains anchored.

## Adaptive live window

The **Live window** control selects the presentation supported by its current host from an explicit user gesture. When the Codex display bridge is present, it requests `fullscreen` and fills that host-managed side panel. The non-scrolling upper region contains the task title, live state, current turn/approximate step/stable record index, record and turn counts, and cumulative Token totals. If projected rate-limit windows are available, an upper-right quota badge shows each window's remaining percentage and exposes its reset time in a tooltip; otherwise the badge is hidden.

The Codex side panel also renders a one-click stop button plus an optional auto-stop guard. The guard defaults to disabled with a whole-percentage threshold of 10, accepts values from 1 through 100, and evaluates `remaining <= threshold` across every valid displayed limit window after live refreshes. A trigger key combines the displayed session, configured threshold, and each displayed window's duration and reset timestamp; it intentionally excludes the running-turn identity. The component saves that key with the enabled state and threshold through `window.openai.setWidgetState`, preventing repeated requests across later turns in the same quota cycle. In the configured Browser view, a separate bounded read-only App Server poll supplies authoritative task activity plus the currently bound turn candidate for Stop/Idle and manual-stop availability; the event ledger remains log-derived and may trail that state. If that poll is temporarily unavailable, the guard still uses the bound trajectory turn for the stop sequence. Before interrupting, the stop endpoint reads `thread/goal/get`; when the task has an active Goal it must successfully change that Goal to `paused` through `thread/goal/set`, then it interrupts the exact bound turn. A confirmed active Goal that cannot be paused is left running and reported as an error rather than creating an interrupt/continuation loop. A successful interrupt becomes **Idle** after the App Server reports that the turn stopped. A rejected stale turn is invalidated and rebound once before a retry, while a later running turn rearms manual stopping without clearing the automatic quota-cycle latch. The latch remains a compatibility and race fallback for durable `/goal` work, including hosts where Goal RPCs are unavailable. Disabling or changing the guard rearms it, observing all windows above the threshold clears the latch, and a changed quota reset timestamp creates a new cycle. A task whose active turn is not running is presented as already stopped: the manual button is disabled, while an enabled, unfired guard stays armed for the next running turn. Transient automatic failures do not consume the latch and retry with exponential delays bounded from 2 to 30 seconds. The constrained Browser endpoint returns the same idle state if the turn finishes between the state poll and the stop request. Successful manual stops also satisfy an already-active automatic quota cycle, preventing the guard from immediately stopping a Goal continuation.

The two host surfaces use the strongest stop primitive they expose. The standard Apps surface calls `window.openai.sendFollowUpMessage` with `scrollToBottom: false` and a fixed prompt asking the task to pause an active Goal when Goal controls are available, stop related subagents, preserve every worktree and uncommitted change, avoid deletion/reset/rollback, and end promptly. The configured in-app Browser instead carries the bound running turn from the trajectory or confirmed state poll into a fixed App Server sequence: `thread/goal/get`, `thread/goal/set(status: "paused")` only for an active Goal, and `turn/interrupt` with the exact thread/turn pair. It does not depend on a sidebar DOM selection, materialize full turn history before stopping, or send arbitrary text. The viewer still binds stopping to the session that opened it, and selecting another trajectory disables both controls. The controls are also disabled when neither channel is available, and the native video PiP fallback does not render them because that surface is not interactive. Auto-stop reacts to the first live snapshot that records a threshold crossing; the one-second polling interval cannot make persisted rate-limit events more granular.

A flex-height event region below the fixed controls scrolls independently through the bounded safe-summary tail in chronological order; every row includes status, duration, and its own Token delta when recorded. That delta is arranged as Total, Input, and Output rows, with uncached/cache details under Input and visible/reasoning details under Output. Follow-latest keeps the newest row at the bottom, but preserves the user's position while they read older rows. A compact transparent 8-by-4 sprite sheet stays clipped inside the newest card's upper-left corner: its 32-frame mining cycle starts when that record's stable identity changes, returns to the first frame after one cycle, does not restart on an unchanged poll, and is suppressed by `prefers-reduced-motion`. The side-panel shell remains mounted and patches only changed fields and record content, keeping the fixed status row stable across one-second checks. The component never requests the unsupported `pip` host mode. When the bridge is absent, it captures a 2:3 canvas as a MediaStream, draws the same compact quota summary in the upper right, feeds the canvas to a hidden video element, and requests Chromium's native always-on-top picture-in-picture window. Neither path launches a standalone application, and a full-detail inline payload is never copied into either live surface. Closing the native window, returning the host to `inline`, or using the component's close control stops live scheduling and refreshes the inline viewer at the detail level that was active before entry.

The app-only `get_codex_trajectory_update` tool accepts `sessionId`, optional `includeArchived`, and an optional 64-character opaque `revision`. Its descriptor uses `ui.visibility: ["app"]`, so it supports the component without becoming a user-facing model tool. The first call, or a call after any lineage file changes, returns a `summary` trajectory capped at 50 latest records plus the next revision. A matching revision returns only `{schemaVersion, unchanged, revision}` and avoids projection parsing. The component issues at most one request at a time every second, stops scheduling while the document is hidden or after the live window exits, resumes immediately when visible, and exponentially backs off to 30 seconds after repeated failures. A source change still requires a complete streaming projection scan to maintain aggregate statistics.

## Optional Codex in-app Browser integration

The current loopback HTTP contract adds an optional bounded `turnId` to the task-state query and requires the same bounded `turnId` in the fixed stop payload, yielding `{sessionId, turnId, source, threshold, language}`. With that candidate, routine state polling uses `thread/read(includeTurns: false)` and returns only running state plus the bound candidate; a full turn read is reserved for bootstrap when the trajectory has not supplied a candidate. If `turn/interrupt` rejects that candidate as stale while the task remains active, the stop result marks it stale, the wrapper invalidates it, and the next state read performs one full bootstrap before a retry.

The inline viewer exposes an experimental, off-by-default switch backed by the app-only `get_codex_toolbar_injection_status` and `set_codex_toolbar_injection` tools. The setter accepts `enabled` plus a loopback port from 1024 through 65535. It atomically stores only `{schemaVersion, enabled, port}` in a mode-0600 plugin-owned file beneath `CODEX_HOME/codex-trajectory`, then starts a detached dependency-free watcher protected by a cross-process lock. A second bounded status file reports the watcher's PID, runtime identity, connection/injection/viewer-serving booleans, a bounded error, and a timestamp; neither file contains transcript content, credentials, the random viewer token, or absolute task-log paths. Settings, heartbeat, and lock reads require bounded single-link regular files. Each MCP runtime start honors the persisted opt-in; when it detects a different installed runtime, it verifies the lock owner, terminates only that outdated watcher, waits for it to release the lock, and then launches the current version.

The watcher connects only to `127.0.0.1`/`localhost` CDP HTTP and WebSocket endpoints, rejects non-loopback debugger URLs, and never follows HTTP redirects during discovery. While enabled it scans at most 100 page/iframe/webview targets once per second, evaluates the token-bearing guarded injector only in Codex-owned `app://` renderers, removes stale injector state from other targets, tries every eligible renderer before reporting bridge failure, and survives SPA/React replacement with a scoped `MutationObserver`. Each WebSocket command has an absolute deadline even if unrelated CDP events continue arriving. It also binds an ephemeral `127.0.0.1` HTTP port and serves a small wrapper plus the exact bundled trajectory app resource beneath a random 256-bit URL token. A same-origin tool bridge accepts bounded interoperable JSON POSTs for only `get_codex_trajectory`, `get_codex_trajectory_update`, `get_codex_toolbar_injection_status`, and `set_codex_toolbar_injection`; duplicate keys and non-finite or oversized numbers are rejected, and all normal MCP argument validation and projection bounds still apply. A read-only theme route accepts no inputs and samples a fixed allowlist of computed Codex CSS colors for the effective background, surfaces, borders, text, accent, success, danger, and event categories. A separate read-only task-state route accepts exactly one bounded session identifier plus an optional bounded turn candidate, reads that bound task through App Server, and returns only a running boolean plus a bounded turn identifier or null. It lets controls follow App Server task activity while the log-derived ledger is delayed. The theme route returns exactly the validated `light`/`dark` effective scheme plus those bounded colors, allowing Codex's System, Light, and Dark appearance choices to update an already-open Browser tab without persisting the palette. A separate stop route accepts exactly `{sessionId, turnId, source, threshold, language}` with bounded identifiers, `manual`/`auto` enum, integer 1–100 threshold, and `en`/`zh` locale. It rejects extra keys and never accepts prompt text. Requests require the exact loopback Host header and token; responses disable caching and apply separate restrictive parent/viewer CSPs. The token is held only in memory and is never written to the status file.

The injected `target="_blank"` link matches the exact visible `Full access`/localized access label and inserts immediately after that control. Immediately before the user's click navigates, it obtains the selected task identifier and locale from Codex and appends them to the tokenized local URL. When the selected sidebar row still uses a `client-new-thread:*` key, the injector resolves the materialized App Server UUID from the active conversation/composer annotations and disables navigation until it exists. Codex handles the user-clicked link as an in-app Browser tab, so Environment/Changes and other native side-panel tabs remain available through the host's own controls. The Browser embeds the same full trajectory app resource as the MCP Apps result and begins with a bounded safe summary; full inputs and outputs still require the resource's explicit confirmation. Opening and browsing the shortcut never reads or writes the composer, activates a send control, posts a task message, or invokes the model. If a stop control fires, the wrapper requires the requested displayed session to match the canonical session that opened the Browser page and supplies its already-bound running turn. The watcher pauses an active Goal first and calls `turn/interrupt` only after that succeeds; older App Servers that report Goal methods as unsupported fall back to the quota-cycle latch. An interrupt error is followed by one history-free `thread/read(includeTurns: false)` state check: a completed turn becomes idle, while a still-active task returns a bounded timeout, stale-turn, or interrupt error. The CDP evaluation deadline covers the bounded App Server requests. Composer drafts and attachments remain untouched. Disabling disposes the observer, removes the injected link, closes the loopback HTTP server, publishes a final heartbeat, and exits.

The app must be launched with a loopback `--remote-debugging-port` before the watcher can connect. Enabling the page setting does not change the app executable, relaunch the app, bind a network listener, or expose the selected port. CDP grants broad page control to local processes, so users must keep it on loopback and avoid tunnels. DOM labels and composer controls are implementation details rather than a documented Codex extension point; failure to match leaves the page unchanged and the watcher keeps retrying until disabled.

## Transport limits

The bundled stdio server implements MCP protocol revision `2025-06-18`, where JSON-RPC batching is not supported. Each newline-delimited request is UTF-8, limited to 8 MiB, and decoded with the same strict duplicate-key and numeric rules as session logs. Requests require a non-null string or finite numeric ID; notifications omit the ID and receive no response. Malformed JSON, invalid requests, invalid parameters, unknown methods, and internal failures use their standard JSON-RPC error classes without exposing local filesystem details.
