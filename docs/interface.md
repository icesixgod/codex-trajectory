# Interface reference

Codex Trajectory exposes three user-facing session MCP tools, four app-only helpers, and one `text/html;profile=mcp-app` resource at `ui://codex-trajectory/trajectory-v2.html`. The viewer uses the native MCP Apps host and exposes no task-control actions. `list_codex_sessions` updates a private derived index and advertises `readOnlyHint: false`; it never edits source task logs.

## Native conversation panel

`open_codex_trajectory` has an empty input schema and app-only visibility. Its descriptor declares `_meta.ui.resourceUri` and `_meta["openai/ui"].entrypoints: [{"type": "thread"}]`. The host can open it from the conversation's right-panel tools menu without a model turn.

The dispatcher passes request `_meta` to this tool without storing task context in global state. On the tested Codex desktop client, `thread_id` and `threadId` contain the calling task ID. Either alias is accepted; both must match when present. Values must be bounded identifiers and resolve to the exact local task, including an archived task. Both successful reads and read-limit errors require an actual matching `session_meta.id` or legacy `session_meta.session_id`; missing or invalid metadata identities return task selection, even when the filename matches. Prefixes, file aliases, process `CODEX_THREAD_ID`, and anonymized `openai/session` metadata never substitute for native caller identity. The same exact-ID check applies to read-limit errors before offering an increased-budget retry; a mismatched or unavailable error identity returns task selection. When compressed metadata cannot be decoded within the current budget, filename-derived identities remain unverified and the native entry returns task selection. Increased-budget retries verify the returned session ID before displaying any trajectory. Missing, invalid, conflicting, or unavailable context returns `{viewerState: "select-session", reason}` with the same UI resource; the user explicitly chooses a task before any trajectory is displayed. This initialization envelope is separate from the frozen trajectory schemas.

`get_codex_trajectory` and `show_codex_trajectory` retain their existing explicit-selector and latest-task behavior. The native entry does not change these public tools' defaults or grant access outside the configured local roots.

`get_codex_trajectory_preferences` takes no arguments and returns `{defaultFullDetails: boolean}`. `set_codex_trajectory_preferences` requires that boolean, atomically persists it in `CODEX_HOME/codex-trajectory/viewer-preferences-v1.json`, and returns the saved value. Both tools are app-only; the setter advertises `readOnlyHint: false`. The setting contains only a schema version and this flag, has private file permissions, and is bounded to 512 bytes on read. Missing, invalid, unreadable, and linked settings mean `false`. The viewer's full-detail confirmation includes a checked option applying the choice to all future tasks on this device. It reads the flag when opened or switching tasks and enables on-demand full details only for an identified task, so revocation in another panel applies on the next task switch. Opening, refresh, selection of another task, and history reads use `detailLevel: "summary"`. An explicit record click (or first confirmation for the current record) requests `detailLevel: "full"`, `maxRecords: 50`, and `beforeRecord: selectedIndex + 1`. Loaded details are held separately from summary records in a 5 MiB panel cache; overlapping pending reads are shared. Refresh, task changes, revocation, and teardown invalidate the cache and outstanding responses; failures are retryable in the inspector. Search includes cached input/output only while full-detail authorization is active and never triggers detail reads. The backend validates the complete lineage once per file signature and selected read budget, building a private temporary safe-summary page index. History and differently sized summary pages then reuse indexed records and aggregate statistics. Full-detail hydration seeks only validated source positions associated with the selected records, including their original calls and late completions; summary projection never formats hidden input/output detail fields. Unchecking the option keeps the choice panel-local, and **Restore safe summary default** persists `false` and reloads a summary. Initial native results, public tool defaults, and live updates remain summaries. No trajectory schema changes are needed.

Oversized tasks return a separate initialization/error envelope with `viewerState: "read-limit-exceeded"`, the selected `sessionId`, and `readLimit: {requiredBytes, currentBytes, suggestedBytes, maximumBytes, atLeast}`. Only byte counts are exposed, never source paths or transcript details. The native entry returns the envelope with its UI resource; read/show/live-update tools mark the same envelope `isError: true`. `atLeast` means the decoder or aggregate scan encountered a lower bound rather than the complete size. The viewer shows the size at the failure point and lets the user explicitly enable a sufficient budget, rounded up to the next decimal GB by default (2.84 GB suggests 3 GB). This envelope is outside the frozen trajectory schemas.

`maxReadBytes` is optional on `get_codex_trajectory`, `show_codex_trajectory`, and the app-only `get_codex_trajectory_update`. It is a positive integer up to 64,000,000,000 bytes and requires an explicit `sessionId`; omission retains 512 MiB. The override is request-local, is included in projection cache identity, and does not expand metadata probes of unrelated files. The viewer keeps the choice in memory per task for this panel's refresh, pagination, detail, and live requests; it is not persisted or applied to other tasks. Reopening the panel restores the default. Explicit larger-budget reads use a ten-minute viewer timeout instead of the normal sixty seconds; the first read still requires a complete streaming scan to validate lineage and compute aggregate statistics.

The bundled dependency-free `mcp-app-bridge.js` initializes MCP Apps protocol `2026-01-26`, sends `ui/notifications/initialized`, calls host `tools/call`, and receives tool results and host-context changes. It consumes theme, supported color variables, locale, and display modes, and answers resource teardown while cancelling pending requests and live polling. It accepts messages only from the parent window. Hosts that expose the legacy `window.openai` bridge retain tool, theme, and display-mode compatibility. Both paths use bounded requests and send no task messages. Locale changes patch all live labels and regenerate translated record descriptions even on unchanged log revisions, preserving expanded records, keyboard focus and the scroll anchor; selection screens also update without reopening or requesting another task.

## Session resolution

Session identifiers must exactly match or unambiguously prefix an identifier discovered below `CODEX_HOME/sessions`; archived target sessions are considered only when `includeArchived` is true. Whitespace surrounding an identifier is ignored, but empty values and strings containing `/` or `\\` are rejected. Exact metadata identities take precedence over filename aliases. Omission means the latest modified active task, not caller identity; `includeArchived` defaults to `false`. Prefix matches must resolve to one target or fail as ambiguous. File paths are never accepted.

Discovery first resolves each configured session root, then accepts only regular files with one filesystem link whose descriptor-checked component chain and final path remain below that root. Descendant symbolic links, reparse points, file hardlinks, FIFOs, and other non-regular sources are excluded. Discovery is capped at 100,000 entries, 10,000 directories, depth 64, and 10,000 rollout files per request. Compact overviews are cached against descriptor-derived modification time, size, and change time for every file in a rollout lineage, so a changed inherited segment invalidates the cache.

When `list_codex_sessions` receives a non-empty query, discovery filters title, identifier, display-safe working directory, and model through a private metadata index before building full overviews. An index miss scans the complete rollout but decodes only metadata-bearing JSONL records; matched candidates alone receive a full overview, and scanning stops at `limit`. The index at `CODEX_HOME/codex-trajectory/session-search-index-v1.json` stores hashed physical and lineage identities, lineage file metadata signatures, and those four bounded search fields. Its title is an excerpt of the first prompt (up to 100 characters), and therefore can be sensitive; it contains no additional transcript bodies, tool details, reasoning, Git metadata, or absolute log paths; it is capped at 10,000 entries and 8 MiB, merged under a cross-process lock with persisted LRU touches and written atomically with mode 0600, rejects linked/reparse files, and fails open to an uncached scan. Any lineage signature change invalidates the corresponding entry.

## Rollout formats

Legacy single-file JSONL and Codex paginated history are both supported in plain `.jsonl` and Zstandard-compressed `.jsonl.zst` files. Python 3.14 uses `compression.zstd`; Python 3.10–3.13 use the pinned `zstandard==0.25.0` dependency. Decompression is materialized into an 8 MiB memory spool that spills to a private temporary file, with a 128 MiB window cap and a 512 MiB default decompressed limit (or the selected task's explicit `maxReadBytes` budget); concatenated frames are accepted, while truncation and trailing garbage fail closed. `history_base.end_byte_offset` always addresses the decompressed logical JSONL stream.

A paginated target is joined oldest-first through official `history_base` pointers, up to 1,024 segments. Current filenames may end in `<thread_uuid>_<rollout_uuid>`: leading metadata must match the thread UUID, while lineage references resolve the immutable rollout UUID. Every segment must use paginated mode, begin at the declared ordinal, remain contiguous, and end exactly at both the declared ordinal and complete-line byte boundary. Paginated wire records without valid leading paginated session metadata, or a missing, ambiguous, cyclic, truncated, overlong, or inconsistent lineage, fail closed. Legacy metadata may appear within the bounded ten-line header probe; paginated metadata must be the leading record. A lineage source may be resolved from either authorized session root even when the selected target is active.

For paginated subagent rollouts, every lineage segment applies its own `subagent_history_start_ordinal`; earlier records in that segment are inherited model context rather than the segment's agent activity and are excluded. This prevents a fork or revert of a migrated subagent from re-exposing the parent's copied context. The target file's first `session_meta` always owns the returned session identity and metadata; an inherited parent's metadata cannot replace it.

## Detail levels

`summary` is the default. It omits record input, output, and metadata; log source paths and Git remotes are never part of the public response. `full` requires an explicit selected session ID and includes bounded record details up to 12,000 characters per field. Both modes exclude `session_meta.base_instructions` and encrypted reasoning content. Persisted reasoning summaries remain visible.

## Projection behavior

`schemaVersion` is `2`. Version 2 adds the required `cost` estimate fields to task statistics, turns, and records. The closed [version 1 schema](../schemas/trajectory-v1.schema.json) remains unchanged for existing validators, while current responses follow the [version 2 schema](../schemas/trajectory-v2.schema.json). Turns use `task_started`, `task_complete`, and `turn_aborted` events where available. Because Codex rollout logs do not persist an authoritative model-step identifier, the projection begins step one with the first model response and increments the approximate step after a tool result when model output resumes.

Tool duration is measured between persisted call and output timestamps unless a completion event provides a duration. A completed record with only one persisted event timestamp has `durationMs: null` because no elapsed interval was measured. Terminal-only raw tools and orphan outputs never use their result timestamp as a call boundary, including repeated outputs and late result markers. A completion-only turn is also untimed unless it carries a start or explicit duration. Unconfirmed durations are `null`: zero, sub-millisecond, invalid, and equal-timestamp intervals do not become measured durations. Explicit unconfirmed completion timing remains unknown even when other timestamps differ or later outputs arrive. If no duration field is supplied, distinct valid call/output boundaries can still provide a measured interval. The viewer renders unknown timing as the literal `-` across the ledger, inspector, live surfaces, turn summaries, and overall duration, including zero values from older hosts. Positive durations at or above one millisecond retain nearest-millisecond rounding. A timing tooltip explains that persisted tool durations may exclude startup, queueing, or asynchronous work; the plugin cannot recover those missing intervals. Aggregate viewer Duration is unknown when any loaded turn is untimed. Explicit completion failures, including MCP `result.Err` values, remain failures when the later tool output is projected. Unknown event types are ignored. A malformed complete JSONL or UTF-8 line produces a warning; an incomplete final JSON or UTF-8 line without a newline is treated as an in-progress write and silently deferred.

The projection recognizes the persisted legacy events and current canonical turn items for user and hook prompts, assistant messages and plans, reasoning summaries, command execution, dynamic and MCP tools, collaboration/subagent activity, web search, image view/generation, extension actions, file changes, review-mode boundaries, and context compaction. A paginated raw `AgentMessage` is also retained because current Codex uses it for inter-agent communication without a canonical turn-item counterpart. Persisted control or metadata events without a user-visible ledger representation are intentionally ignored; `thread_rolled_back` instead emits a warning that earlier projected execution remains a historical record. Canonical `item_completed` records own their declared turn; a mismatched turn closes the prior turn as aborted so overview and detail counts do not diverge.

The viewer labels reasoning records **Analysis & decision** (**分析与决策** in Chinese) and puts the original saved text first in a wrapping Content preview. A recognizable activity receives a short localized label underneath; unrecognized or negated text remains visible without an inferred label. Conservative local rules still inspect only the summary's initial heading or first sentence for activity cues. With explicit full details, the preview uses up to 600 characters from the saved reasoning `output`, and the inspector shows the bounded longer summary directly, preserving paragraph breaks and escaping all text. Hover text uses at most 1,200 characters. The original 220-character `summary` and `event` and the frozen response schemas remain unchanged. If no readable summary was saved, Content directly supplies the nearest non-reasoning events before and after it, with record indexes and safe descriptions, or a dash when none are loaded. The missing-summary explanation stays in hover text and the inspector, rather than prefixing every ledger or live preview; the inspector explicitly reports when no context is loaded. Context is labeled as recorded surrounding activity, never reconstructed analysis or a causal explanation. Links remain inside the same turn and stop at missing stable indexes. Neighbor lookup is indexed once per record-page array, so rendering many unavailable summaries stays linear in the loaded page size. These rules apply to every project. Live surfaces use only their own safe-summary record arrays, wrap their loaded summaries in full in the side panel, and never consult the inline viewer's full details or broader history. No model call, hidden tool details, or encrypted reasoning is used.

Canonical `CommandExecution` records retain a fixed allowlisted activity description in `summary`, formatted as `Command: Read files + Search text · complete · exit 0` when known. At most four distinct activities are retained; arguments, paths, search patterns, and output text are never copied into that description. The optional exit code must be a non-boolean signed 32-bit integer. Command activity detection accepts bounded argument vectors and simple POSIX shell sequences, including common interpreter and `uv run` wrappers; opaque script bodies, command substitutions, redirections, malformed or oversized inputs, and unknown commands fall back conservatively. Shell text is parsed locally and never executed. Terminal updates and late completion markers preserve this activity description. The frozen v2 schema and raw full-detail fields are unchanged. The viewer translates known activities, displays execution state separately, labels `complete` as **Ended** (**已结束**), and makes no claim that a test or task succeeded. Older `Command · complete` summaries receive an explicit unknown-purpose explanation. The same descriptions appear in hover text, the inspector, related reasoning context, and safe live views.

When cumulative `total_token_usage` changes, its per-counter deltas take precedence over missing or inconsistent `last_token_usage` values. A decrease in any provided cumulative counter starts a new epoch for the whole snapshot, including counters whose new values already exceed the previous epoch. Missing counters do not retain old-epoch baselines. Normalized usage is accumulated into its owning turn; record-level `usage` and `cost` remain `null` for frozen v2 schema compatibility; repeated cumulative snapshots and initial zero snapshots are ignored. When older logs omit a cumulative snapshot, the `last_token_usage` sample retains the legacy behavior and is counted. `modelCalls` counts the accepted usage samples. Each turn also captures the model active in its `turn_context`, falling back to the session model in the viewer. Each turn header displays uncached-input, cached-input, and output totals. Indexed ledger rows contain only Index, Step, Event, Content, and Time, and the record inspector shows no usage or cost estimate. Uncached input is derived as `max(0, input_tokens - cached_input_tokens)`. Session totals sum accepted deltas across counter resets, matching the overview. The viewer labels duration and request counts as loaded-turn metrics when turns are omitted, while task token and cost totals cover the whole parsed history. Cached-input and reasoning-output values are breakdowns within input and output, so clients must not add them to `total_tokens`. Cumulative session input is not a context-window measurement.

Every accepted usage sample is also priced against an explicit allowlist snapshot of standard OpenAI API text-token rates, updated 2026-10-01. The snapshot covers GPT-6.1 Sol, GPT-6 Astra, GPT-6 Sol, and GPT-6 Luna, with each model's published cache-read rate, and retains GPT-5.6 Sol's current promotional standard rate, advertised through at least 2026-11-21. `turn.cost` accumulates the owning turn, and `stats.cost` accumulates the complete parsed task independently of record pagination. Accepted usage samples are priced once, without attaching estimates to individual records. Each estimate reports USD totals for uncached input, cached input, and output; reasoning output is already included in output and is not charged twice. `coverage` is `complete`, `partial`, or `unavailable`, with priced and unpriced model-call counts. Exact published model IDs and dated snapshots are supported; unknown and Codex-only model aliases without a published API rate remain unpriced instead of inheriting a guessed family rate. The estimate starts from standard token pricing and is not a Codex subscription bill. Tool-call fees, cache writes, long-context multipliers, Batch/Flex/Fast/Ultrafast tiers, and regional processing adjustments are excluded. Pricing is local and performs no runtime network lookup. For explicitly persisted `fast`/`priority` calls, the viewer's requested Codex included-usage estimate multiplies all billable components by 2.5; this is a subscription-usage proxy, not API or purchased-credit billing. The usage snapshot's `service_tier` overrides the requested turn-context tier. The model output's tier is retained for delayed usage attribution across context/turn changes. A missing tier in a new context clears the previous tier; current machine configuration is never used to reconstruct historical mode. Duplicate cumulative samples do not reapply pricing. An existing warning envelope with code `codex_fast_cost_multiplier` reports applied Fast estimates and is preserved within the warning bound, without extending frozen cost/turn schemas. The viewer disables the manual multiplier for these marked tasks to prevent double application. When no Fast notice exists, the per-task, panel-only **Task cost mode** selector can manually display the whole task at ×2.5; it changes formatting of immutable estimates, leaves token counts untouched, and is shared by main, turn, native video PiP, and docked live views. Reopening the panel resets this manual assumption; the plugin-owned persisted full-detail preference is unchanged. Reinstalling a local plugin does not refresh an existing task's loaded price table or projection caches; fully quit and reopen the desktop app before reopening that task's viewer.

The latest valid persisted `rate_limits` snapshot is exposed as `stats.rateLimits`. Only the bounded `primary` and `secondary` windows are projected, each with `usedPercent`, `windowMinutes`, and an optional normalized `resetsAt`; plan, credit, account, and unknown fields are excluded. Partial valid snapshots update only their valid windows; explicit null windows remove previous values, and snapshots for non-Codex limit buckets are ignored. The live viewer calculates remaining allowance as `max(0, 100 - usedPercent)` and never substitutes Token totals or the model context window when account quota data is absent.

The log is parsed incrementally, and only one `maxRecords` page is retained and returned with stable original `index` values. Without `beforeRecord`, this is the newest tail. With an exclusive `beforeRecord` index, the response contains the closest preceding records whose indexes are lower than the cursor. The `pagination` object reports the first and last returned indexes, earlier and later record counts, both direction flags, and `nextBeforeRecord`; pass that next cursor unchanged to retrieve the adjacent older page. Aggregate statistics continue to describe the complete parsed task, independent of page selection. At most 1,000 records and 1,000 visible turns are returned per response; every visible record's owning turn is retained before remaining slots are filled with the newest turns. Warnings are capped at 100, and active tool correlation is bounded independently of the page so projection indexes do not change between page requests. Text summaries and full-detail fields are bounded independently. Serialized records are additionally capped at 5 MiB per page (ASCII-escaped sizing), reducing the page and preserving its older-page cursor when needed. The process projection cache is capped at 16 entries and 24 MiB of serialized payload. A logical rollout defaults to a 512 MiB byte budget, optionally raised by the selected task's explicit `maxReadBytes`; the 1,000,000-physical-line cap remains; each complete JSONL line is capped at 16 MiB. Duplicate object keys, `NaN`/infinity, floats outside the finite range, integers over 256 digits, and non-object records are never projected as valid entries.

`get_codex_trajectory` and `show_codex_trajectory` do not eagerly attach recent-session overviews to the trajectory payload. After the selected trajectory has rendered, the viewer makes one `list_codex_sessions` request for its selector. The optional schema-v1 `recentSessions` property remains accepted for backward-compatible callers.

The viewer targets Codex desktop surfaces and desktop Chromium browsers. It initially materializes ledger records for the latest loaded turn only. Earlier turn headers remain available, and clicking anywhere on a turn summary row—including its uncached-input, cache-read, and output totals—adds or removes that turn's records from the DOM; filtering or selecting a hidden record reveals it automatically. Each expanded turn materializes its own sticky ledger-column header, scoped to that turn's row group. Record rows therefore show only the approximate Step, while the owning turn remains visible in the group header and full Turn/step context remains in the inspector. The report preserves 15px body text and labels of at least 12px. Event and Content wrap in proportional desktop columns. At widths of 700px and below, each record becomes a vertical card with labeled Index, Step, and Time above the event and content; column headers remain accessible to assistive technology. Hover and focus tooltips supply additional context. Large session Token totals use responsive tabular-number sizing and are never ellipsized; the per-turn Token table uses labeled four-column metric grids, two columns at 700px and below, and one at 360px and below. The collapsed per-turn table is materialized only when opened. Viewer-initiated full refreshes request the default 500-record tail rather than the 1,000-record maximum. When earlier records exist, **Load earlier records** requests the adjacent 500-record page, merges records and turns by stable index, deduplicates warnings, and compensates for the prepended ledger height so the current viewport remains anchored. The merged history is a sliding window of at most 5,000 records and a conservative 20 MiB serialized-size estimate; newer records are dropped at the cap. Refresh returns to the latest tail. Controls have 44px minimum touch targets (excluding timeline markers) and wrap at small widths. At 1380px and below the inspector is below the ledger; selecting a record scrolls and focuses its details, and **Back to records** restores the selected row and keyboard focus. Long IDs, paths, text, and raw details wrap instead of requiring horizontal scrolling. The timeline supports +/- zoom, arrow-key panning, and Escape reset.

JSON input/output details are formatted incrementally within a 12,000-character budget, including the truncation notice. Strings and object keys are escaped in bounded chunks; nested containers stop as soon as the displayed prefix fills the budget. Small JSON values retain standard two-space indentation. Truncated JSON uses `… truncated additional characters` without an exact omitted-character count, so formatting never builds or traverses the complete omitted output merely to count it. Non-JSON diagnostic fallbacks also use bounded representations. Plain-text fields retain their existing truncation behavior.

JSON 输入和输出详情在格式化过程中执行 12,000 字符预算，包含截断提示。字符串和对象键分块转义，嵌套容器达到显示预算后立即停止处理；小 JSON 保留原有的双空格缩进。截断时显示 `… truncated additional characters`，不再为了统计省略字符数而生成或遍历全部剩余输出。非 JSON 诊断文本也使用受限表示，普通文本字段保留原有截断行为。

## Adaptive live window

The **Live window** control selects the presentation supported by its current host from an explicit user gesture. When the Codex display bridge is present, it requests `fullscreen` and fills that host-managed side panel. The upper region is capped at 58% of the viewport height and has independent vertical scrolling when needed; it contains the task title, live state, current turn/approximate step/stable record index, record and turn counts, cumulative Token totals, total estimated cost, and current-turn estimated cost. The app-only live-update envelope includes `quota: {rateLimits, sampledAt}` on both changed and unchanged task revisions. This is separate from the frozen trajectory payload: public `stats.rateLimits` remains the selected task's persisted snapshot. Live quota uses the newest event timestamp among the 32 most recently modified active local rollout files, reading at most 256 KiB per plain-file tail and decoding only complete quota event lines of at most 64 KiB. Compressed candidates are skipped rather than decompressed for quota polling. Descriptor-checked signatures reuse bounded, sanitized in-memory samples for unchanged files and growth of the same file. Samples that roll outside the bounded tail remain cached, and newer partial updates merge with known windows; older timestamps cannot replace the cached sample. Replacement, truncation, or edits without file growth invalidate that file's sample, while explicit null windows remove their cached values. Inference-reserve buckets are excluded; missing samples return null values and hide the badge. Another task's quota change does not reparse the selected trajectory. The badge tooltip includes reset and sample times.

The viewer provides no stopping or quota-triggered actions. Task status follows the selected task; quota follows recent local active-task samples and may lag the account service. A changed account or another device's activity cannot be detected until a new local Codex sample is written.

A flex-height event region below the fixed controls scrolls independently through the bounded safe-summary tail in chronological order. Sticky turn dividers show each visible turn's Token total and estimated cost; event rows show their safe summary, status, and duration. Each side-panel or in-page card has a native keyboard-accessible disclosure for safe timing, call ID, and loaded summary details. Expansion is keyed by stable record identity, retained across polls only while the record remains in the bounded tail, and cleared on exit. Stream updates restore disclosure focus and preserve the reading position; expanded details pause follow-latest. Expanding a live card makes no full-detail tool request and never uses the inline detail cache. Record-level usage and cost are omitted from all live surfaces. Follow-latest keeps the newest row at the bottom, but preserves the user's position while they read older rows. A compact transparent 8-by-4 sprite sheet stays clipped inside the newest card's upper-left corner: its 32-frame mining cycle starts when that record's stable identity changes, returns to the first frame after one cycle, does not restart on an unchanged poll, and is suppressed by `prefers-reduced-motion`. The side-panel shell remains mounted and patches only changed fields and record content, keeping the fixed status row stable across one-second checks. The component never requests the unsupported `pip` host mode. When the bridge is absent, it captures a 2:3 canvas as a MediaStream, draws task and current-turn cost estimates with the compact quota summary, feeds the canvas to a hidden video element, and requests Chromium's native always-on-top picture-in-picture window. Neither path launches a standalone application, and a full-detail inline payload is never copied into either live surface. Closing the native window, returning the host to `inline`, or using the component's close control stops live scheduling and refreshes the inline viewer at the detail level that was active before entry.

The app-only `get_codex_trajectory_update` tool accepts `sessionId`, optional `includeArchived` and `maxReadBytes`, and an optional 64-character opaque `revision`. Its descriptor uses `ui.visibility: ["app"]`, so it supports the component without becoming a user-facing model tool. The first call, or a call after any lineage file changes, returns a `summary` trajectory capped at 50 latest records plus the next revision. A matching revision returns only `{schemaVersion, unchanged, revision}` and avoids projection parsing. The component issues at most one request at a time every second, stops scheduling while the document is hidden or after the live window exits, resumes immediately when visible, and exponentially backs off to 30 seconds after repeated failures. A source change still requires a complete streaming projection scan to maintain aggregate statistics.

## Transport limits

The bundled stdio server implements MCP protocol revision `2025-06-18`, where JSON-RPC batching is not supported. Each newline-delimited request is UTF-8, limited to 8 MiB, and decoded with the same strict duplicate-key and numeric rules as session logs. Every encoded response, including its newline, is also limited to 8 MiB; oversized successful results become a bounded error, so callers should paginate rather than request an unbounded full transcript. Requests require a non-null string or finite numeric ID; notifications omit the ID and receive no response. The server requires initialize followed by notifications/initialized before business requests. Request-only methods never execute as notifications. Ping, initialization, and cancellation are handled promptly in the reader while one worker executes business requests serially; the bounded 8-request waiting queue rejects overflow instead of blocking control traffic. Duplicate in-flight IDs are rejected. Cancellation suppresses responses and skips cancelled queued work, but running projections are not preempted. Malformed JSON, invalid requests, invalid parameters, unknown methods/resources, and internal failures use stable JSON-RPC error classes without exposing local filesystem details.

## Temporary trajectory page index

Successful trajectory tool envelopes include `_meta["codex-trajectory/revision"]`, an opaque SHA-256 of the validated lineage signature, when that signature is unchanged across the read. This metadata does not extend either frozen trajectory schema. Summaries of actively changing logs remain readable but do not claim a stable revision. The viewer binds detail pages by matching source revision, session ID and stable record index, independent of page-local record ID collision disambiguation. A changed or unavailable revision requires refresh before attaching details; legacy envelopes without revisions retain exact record-ID checks. History pages require matching revisions whenever either side supplies one; a missing initial revision requires refresh before merging a versioned history page. Only two legacy envelopes without revisions may use the compatibility merge path.

The process builds a temporary SQLite index while projecting safe summaries. It retains every projected record's stable index, bounded summary and turn data, aggregate results, and the validated logical source positions needed to hydrate selected details. Tool bodies, raw record metadata, base instructions, and encrypted reasoning are never written to the index. Internal source paths and offsets stay local in a private temporary directory and are never included in tool responses. Limits are 128 MiB per index and four indexes / 256 MiB per process; oversized indexes fall back to streaming projection. Eviction and normal process exit remove the temporary directory. Abrupt termination may leave an OS temporary directory, which can be deleted safely.

Index identity includes every lineage file's descriptor-checked metadata signature and the request's read budget. A different read budget cannot reuse an authorized larger-budget index to bypass the default limit. Detail hydration opens sources through the same single-link, root-contained descriptor checks and strictly decodes only indexed complete lines. It reconstructs original calls and late tool completions before filling bounded full-detail fields; aggregate counts, token accounting, costs and timing come from the validated complete summary. The summary index tracks bounded normalized record and call IDs before page-local collision disambiguation. If an independent record or call ID is reused, summary and full-detail pages use the canonical streaming parser. This preserves unique record IDs when a later request enlarges the initial page, as well as the original detail associations. Automatically generated late-result markers inherit the original call and do not count as independent reuse. Compressed segments still need decompression into the existing bounded spool before seeking their logical offsets.
