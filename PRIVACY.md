# Privacy Policy

Codex Trajectory runs locally and reads Codex JSONL task logs from `CODEX_HOME/sessions` and, when requested for a target, `CODEX_HOME/archived_sessions`. Paginated targets may inherit earlier segments from either authorized root; copied parent context before a subagent's declared history boundary is excluded from that child trajectory.

The plugin does not edit task logs, persist a secondary copy of them, or add telemetry. Its Python runtime makes no application network requests unless the user explicitly enables the experimental CDP in-app Browser integration; that integration uses only loopback debugging and viewer ports and rejects non-loopback debugger WebSocket URLs. The `uv` launcher may provision a compatible Python according to the user's own uv configuration. The trajectory tools accept session identifiers rather than paths and exclude descendant symlinks, file hardlinks, and files outside the configured roots. Safe summary mode is the default: tool inputs, tool outputs, raw record metadata, absolute log paths, Git remotes, base instructions, and encrypted reasoning are not returned. Full-detail mode requires an explicit tool parameter or confirmation in the viewer; it returns bounded tool inputs and outputs but still excludes base instructions and encrypted reasoning. All returned collections and text fields are bounded.

The CDP integration is off by default. Its app-only setter stores the enabled flag and loopback debugging port in a private plugin-owned file under `CODEX_HOME/codex-trajectory`; a second bounded heartbeat stores process/runtime booleans, a timestamp, and at most 500 characters of local error text. Settings, heartbeat, and watcher-lock reads accept only bounded single-link regular files and reject symbolic links, hardlinks, non-regular files, and oversized content. The watcher evaluates the token-bearing injector only in Codex-owned `app://` renderer targets, removes stale injector state from other discovered targets, tries every eligible renderer before reporting bridge failure, places one link next to the visible `Full access` control, and serves the bundled trajectory interface from a random `127.0.0.1` port beneath a random 256-bit URL token. Direct CDP discovery requests do not follow HTTP redirects, and local JSON boundaries reject duplicate keys and non-finite or oversized numbers. The token remains in process memory and is not persisted. A click reads only the active sidebar task identifier, the canonical conversation identifier exposed by the active composer or response annotations when the sidebar still uses `client-new-thread:*`, and the locale needed to open that task in the Codex in-app Browser; the link remains disabled until a canonical identifier is available. While that page is open, a separate read-only theme route samples only a fixed allowlist of computed Codex background, surface, border, text, status, and accent CSS colors; it returns those values to the loopback page so System, Light, and Dark appearances stay matched, and neither stores nor sends them remotely. A second read-only route reads the task identifier already bound to the Browser page through the local App Server bridge and returns only whether it is active plus a bounded turn candidate or null, allowing Stop/Idle to remain accurate while log persistence lags. The page begins with the same bounded safe-summary fields as the MCP viewer; full details require the same explicit confirmation and retain the same projection bounds and exclusions. Its local tool bridge allows only trajectory reads/updates and the plugin's own CDP setting/status calls. Opening and browsing the page does not read or write composer content, post a task message, invoke the model, add telemetry, or contact a remote host. The Browser stop endpoint and standard Apps component's app-private stop tool accept only validated identifiers, `manual`/`auto` source, integer threshold, and locale; they reject extra fields and arbitrary prompt text. The private tool may resolve a missing turn candidate or rebind one stale candidate, but it acts only while the persisted CDP opt-in is enabled. A stop reads the bound task's Goal state through `thread/goal/get`, changes an active Goal to `paused` through `thread/goal/set`, and then calls `turn/interrupt`. This intentional Goal-status write is limited to a user-clicked or explicitly user-armed stop action; a confirmed active Goal that cannot be paused is not interrupted. No transcript body is retained. Neither stop path reads or changes composer drafts or attachments. Disabling the integration removes the injected DOM, closes the local page server, stops the watcher, and disables standard Apps stop controls. Once enabled, a later MCP runtime start may replace only the verified watcher holding the plugin-owned lock so an installed update takes effect. Because a CDP debugging port permits broad application-page control by local processes, users must bind it only to loopback and must not expose it through tunnels or a non-loopback address.

The optional one-click stop control and user-armed quota guard use only the explicitly enabled local direct-stop path. The standard side panel invokes the app-private MCP action, and the configured Browser uses its session-bound endpoint; both directly pause an active Goal and interrupt the bound App Server turn. They do not invoke the model, post a task or follow-up message, enter the steering queue, delete or clean worktrees, or kill unrelated operating-system processes. When direct CDP is unavailable, the controls fail closed instead of substituting a model-mediated message. The guard defaults to off; its threshold, enabled state, and one-shot quota-cycle latch are stored through the host's widget-state facility when available.

When a user invokes the plugin through Codex, structured results may become part of the active Codex conversation and may therefore be processed according to the user's Codex service configuration. Users should review task contents before enabling full details.

Questions or deletion requests do not apply to a project-operated service because this project stores no user data. Security-sensitive reports should follow [SECURITY.md](SECURITY.md).
